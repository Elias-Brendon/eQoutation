# Version System + No-Hardcoded-Paths Audit Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the project a repeatable local version-bump + changelog workflow (`standard-version`), bootstrapped cleanly against the existing 111-commit history, with the workflow documented for future releases.

**Architecture:** Add `standard-version` as a devDependency with a single `npm run release` script. Bootstrap it once with `--first-release` so it tags the current `0.1.0` and starts `CHANGELOG.md` from a clean baseline (not mining pre-convention history). Document the ongoing release steps in `README.md`. No application code changes — this is tooling/config/docs only. The no-hardcoded-paths audit found no violations (see the spec's Section 1); it is recorded as a note in this plan's final task rather than a separate code task.

**Tech Stack:** npm, `standard-version` (CLI devDependency), existing conventional-commit convention (`feat:`/`fix:`/`chore:`) already used in this repo's git history.

## Global Constraints

- Plain semver only — no prerelease identifiers (e.g. no `-beta.N`). Source: spec Section 2, "Versioning scheme."
- The first `standard-version` run MUST use `--first-release` so it does not mine the 111 pre-existing commits (only 14 of which are non-conventional, all early "Stage N" commits) into the changelog. Source: spec Section 2, "Bootstrap."
- No CI integration — this stays a manual local step run before building a beta installer. Source: spec Section 2, "Ongoing workflow."
- `CHANGELOG.md` must NOT be shipped in the packaged app. `electron-builder.yml` already excludes it (added in sub-project 1) — verify, do not re-add.
- No changes to the About panel, `app:getVersion` IPC, or `useAppVersion` hook — they already read the version live and need no modification. Source: spec Section 2, "No changes needed to existing version display."

### Task 1: Install standard-version and add the release script

**Files:**
- Modify: `package.json` (add devDependency, add `release` script)
- Modify: `package-lock.json` (updated automatically by `npm install`)

**Interfaces:**
- Produces: an `npm run release` command usable by Task 2 and by the documented workflow in Task 3.

- [ ] **Step 1: Install the package**

Run:
```bash
npm install --save-dev standard-version
```
Expected: `package.json` gains a `"standard-version": "^X.Y.Z"` entry under `devDependencies`; `package-lock.json` updates accordingly.

- [ ] **Step 2: Add the release script**

In `package.json`, add this entry to the `"scripts"` object (alongside the existing `"postinstall"`/`"build:*"` entries):

```json
"release": "standard-version",
```

- [ ] **Step 3: Verify the tool runs correctly (dry run, no writes)**

Run:
```bash
npx standard-version --dry-run
```
Expected: the command completes without error and prints a proposed version bump and changelog preview to the console (this preview will include old "Stage N" commits since no tag exists yet — that is expected and fine, since `--dry-run` writes nothing to disk; Task 2 will bootstrap correctly with `--first-release`). If the command errors, do not proceed to Task 2 — resolve the error first (most likely cause: no commits are conventionally formatted, or the package installed incorrectly).

- [ ] **Step 4: Commit**

```bash
git add package.json package-lock.json
git commit -m "chore: add standard-version for release/changelog management"
```

### Task 2: Bootstrap the first release (CHANGELOG.md + v0.1.0 tag)

**Files:**
- Create: `CHANGELOG.md` (generated by `standard-version`)
- Modify: `package.json` (version field — expected to remain `0.1.0`, unchanged, since `--first-release` skips bumping)

**Interfaces:**
- Consumes: the `npm run release` script from Task 1.
- Produces: a `v0.1.0` git tag and a baseline `CHANGELOG.md`, which all future `npm run release` invocations (documented in Task 3) will build on top of.

- [ ] **Step 1: Run the bootstrap release**

```bash
npx standard-version --first-release
```
Expected output: a new `CHANGELOG.md` file is created, `package.json`'s `"version"` field remains `"0.1.0"` (not bumped), a git commit is created (message like `chore(release): 0.1.0`), and a `v0.1.0` git tag is created pointing at that commit.

- [ ] **Step 2: Verify CHANGELOG.md is a clean baseline, not mined history**

Read `CHANGELOG.md`. Expected: it contains a version header (`# 0.1.0 (...)` or similar) with either no entries or a very short list, and does NOT contain a long list of every commit back to `Stage 0: scaffold eQoutation Electron app`. If it does contain the full mined history, `--first-release` was not applied correctly — stop and re-check Step 1 before continuing (do not proceed with a messy changelog).

- [ ] **Step 3: Verify the tag was created**

Run:
```bash
git tag --list v0.1.0
git log -1 --format=%s
```
Expected: `v0.1.0` is listed, and the latest commit message is the release commit created in Step 1 (not the `chore: add standard-version...` commit from Task 1 — that should be the parent).

- [ ] **Step 4: Verify electron-builder still excludes CHANGELOG.md from the packaged app**

Run:
```bash
grep -n "CHANGELOG.md" electron-builder.yml
```
Expected: the existing exclusion line from sub-project 1 (`'!{.eslintcache,eslint.config.mjs,.prettierignore,.prettierrc.yaml,dev-app-update.yml,CHANGELOG.md,README.md}'`) is present. No edit needed — this step is verification only. If it is somehow missing, add `CHANGELOG.md` back into that exclusion list before continuing.

(No separate commit step here — Step 1's `standard-version` run already created the commit and tag.)

### Task 3: Document the release workflow in README.md, and record the path-audit finding

**Files:**
- Modify: `README.md:23-34` (add a "Release" section after the existing "Build" section)

**Interfaces:**
- Consumes: the `npm run release` command from Task 1, the bootstrap outcome from Task 2.
- Produces: nothing consumed by later tasks — this is the terminal documentation task.

- [ ] **Step 1: Add a Release section to README.md**

After the existing `### Build` section (ends at line 34 with the closing ` ``` `), append:

```markdown

### Release

Before building a beta installer, bump the version and update the changelog:

```bash
npm run release
```

This uses [standard-version](https://github.com/absolute-version/commit-and-tag-version) to read conventional commit messages (`feat:`, `fix:`, `chore:`, etc.) since the last tag, bump `package.json`'s version accordingly (plain semver, no prerelease suffix — this project stays under `1.0.0` during beta), prepend a new entry to `CHANGELOG.md`, and create a `chore(release): X.Y.Z` commit with a matching `vX.Y.Z` git tag.

After running it:

```bash
git push --follow-tags
```

Then build the installer as usual (`npm run build:win`, etc.) — the version baked into the app now matches the tag.
```
